# V9.2 — General Error Handling: What Changed
 
A summary of the work done for this version, in plain terms.
 
## The problem we started with
 
The agent had no consistent way of handling things going wrong — a
Gemini API failure, a bad LLM response, or MongoDB/AstraDB being
unreachable could all crash a turn and dump a raw error in front of
the user. There was also no fallback messaging, and rate limits (429s)
were being handled manually by swapping API keys by hand.
 
## What we built
 
**A shared error-handling layer** (`agent/error_handling.py`) that the
rest of the app now goes through for any LLM call:
- If a call to Gemini fails, it retries once automatically.
- If a structured/JSON response from Gemini comes back malformed, it
  asks the model again once, including what went wrong.
- If a call fails because of a rate limit or because a model isn't
  available on the current API key, it automatically switches to the
  next configured Gemini key and retries — instead of failing outright
  or requiring a manual key swap. It cycles through all configured
  keys once before giving up, rather than retrying forever.
**A shared LLM setup file** (`agent/llm.py`) so both the main coach
chat and the monthly review pipeline build their Gemini clients the
same way, instead of duplicating that logic.
 
**Database failure handling** (`db/guards.py`) applied across the
tools the agent uses:
- If MongoDB is unreachable, the affected action now fails cleanly
  with a plain "couldn't reach your saved data, try again" message
  instead of crashing or showing a raw database error.
- If the fitness knowledge base (AstraDB) is unreachable, the agent
  just proceeds without that extra context instead of erroring out —
  this one's treated as low-stakes since it only affects supplementary
  info, not saved data.
- Care was taken to only apply this at the right spots — some internal
  helper functions return "empty" as a normal, valid result (e.g. "no
  goal set yet"), so wrapping those directly would have made a real
  outage indistinguishable from an ordinary empty result. Those were
  left alone and the failure handling was placed at the outer,
  user-facing function instead.
**Conversation-level fallbacks**, so a failure never ends in a crash
the user sees:
- If the main coach LLM fails even after retrying, the user gets a
  calm, in-character message asking them to try again, instead of an
  error.
- If something fails before the LLM is even reached (e.g. syncing
  backlog data, loading the user's current goal), the chat interface
  catches it and shows a similar friendly message rather than crashing
  the app.
- A daily check-in lookup that runs automatically at the start of
  every session now fails silently and just continues without
  yesterday's context, rather than blocking the conversation.
**Monthly review pipeline** — the same retry/fallback approach was
extended here: if the AI-generated summary or the next month's themes
can't be produced even after retrying, a sensible fallback is used
(previously this pipeline just crashed with no fallback in one place).
Database writes here also now fail cleanly rather than partially
saving. Also fixed a pre-existing bug in the Streamlit page where this
pipeline's result was being read incorrectly, always showing an error
message even when the review had actually succeeded.
 
## Notable decisions worth knowing about
 
- **API key rotation** wasn't part of the original plan for this
  version — it was added once we realized rate limits were a real,
  recurring pain point. It's a deliberate small expansion of scope,
  documented in the design doc as an addendum.
- Retry behavior everywhere is intentionally simple: no fancy
  backoff, no configurable retry counts — one retry, or one pass
  through the available API keys, then stop and fall back.
- Nothing about how the agent decides what to do changed — this
  version is entirely about what happens when something goes wrong,
  not the agent's actual coaching logic.
