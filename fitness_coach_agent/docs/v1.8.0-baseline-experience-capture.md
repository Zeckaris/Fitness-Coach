# v1.8.0 Design Summary: Baseline Experience Capture

## Core Problem

`experience_level` (`beginner` / `intermediate` / `advanced`) currently has **zero persistence** anywhere in the system. It exists only as a transient parameter on `CalculateVolumeTargetInput` and `calculate_month_target()`, and is set entirely by LLM inference from free-text conversation — never by directly asking the user.

The system prompt instructs the LLM to default to `"beginner"` and only escalate if the user's own stated numbers or explicit claims support it (e.g. "I've been training for years"). There is no structured question, no onboarding step, no profile field. Three independent code paths each redundantly default to `"beginner"` if the parameter is omitted (`tools/month_plans.py:122`, `tools/month_plans.py:142`, `utils/baseline_targets.py:84`).

The only downstream consumer of `experience_level` is the `INTENSITY_FACTOR` lookup inside `calculate_month_target()` (beginner=0.75, intermediate=0.80, advanced=0.85), which directly scales monthly volume targets. Since this is silently wrong for most returning or self-reporting-shy users, monthly targets are frequently miscalibrated from day one.

## Discovery Findings (pre-design)

- `users` collection: only `email`, `password_hash`, `created_at` — no profile fields whatsoever.
- No onboarding/questionnaire UI pattern exists anywhere in the Streamlit app (`app/streamlit_app.py`); the only form is email/password auth.
- No "days since last activity" computation exists, though raw timestamps (`plans.completed_at`, checkin dates, metric dates) could support one.
- Injury handling already exists via `record_checkin` → `checkins` collection: a flat, daily-overwritten `Optional[str]` free-text field, translated into `avoid_body_parts` by the LLM (no deterministic parsing), with no expiration/resolution concept. **Left untouched for v1.8** — a structured/persistent upgrade to injury tracking is a separate future item, not folded into this pass.
- Beverage logging already exists via `record_checkin` (`Beverage{name, amount_ml}` list, pushed daily into `checkins`) — purely conversational context today, no aggregation. Not touched by v1.8.
- A `metrics` collection/tool already exists for logging weight/measurements over time (one entry per log event). **v1.8 extends this** rather than creating a new time-series collection.

## Design Decisions

- **Trigger conditions**: baseline questionnaire required for first-time registered users, and for users who haven't completed a workout in 3+ months (exact "days inactive" query TBD during implementation, built on top of `plans.completed_at`).
- **Where it happens**: a new **blocking Streamlit onboarding screen**, shown before dashboard access — not an in-chat conversation, not a dismissible banner.
- **What it measures**: concrete performance markers (max push-ups, max bodyweight squats, longest continuous run, current weekly workout frequency, and a conditional weighted-lift marker for users with weight access) — not self-reported training history.
- **Existing users**: no migration needed. Current data is test data only; only new signups go through onboarding.
- **Units**: stored as the user enters them (not normalized to metric) — `weight_unit_preference` / `height_unit_preference` fields track which unit was used.
- **Height**: captured at onboarding but **not used in the leveling formula**. Reserved for future features (BMI, calorie estimation).

## Baseline → Level Formula

Research-verified against real strength-standard data, then calibrated to a **general-population framing** (not elite/leaderboard framing — public strength-standard datasets like strengthlevel.com skew high because their user base is self-selected serious lifters).

```
threshold = base_value(gender) × bodyweight_factor(weight) × age_factor(age)
```

### Base values (reference: 70kg male / 60kg female, age ≤ 40)

| Marker | Male | Female |
|---|---|---|
| Push-ups (max reps) | Beginner < 10, Intermediate 10–24, Advanced 25+ | Beginner < 6, Intermediate 6–17, Advanced 18+ |
| Bodyweight squats (max reps) | Beginner < 15, Intermediate 15–39, Advanced 40+ | Beginner < 11, Intermediate 11–27, Advanced 28+ |
| Weighted lift — 8-rep goblet squat or DB press, kg (conditional, only if user has weight access) | Beginner < 0.17× BW, Intermediate 0.17–0.47× BW, Advanced 0.47×+ BW | Beginner < 0.13× BW, Intermediate 0.13–0.34× BW, Advanced 0.34×+ BW |
| Longest continuous run | Beginner < 15 min, Intermediate 15–29 min, Advanced 30+ min (unisex, unscaled) |
| Current weekly workout frequency | Beginner 0–1×/week, Intermediate 2–3×/week, Advanced 4+×/week (unisex, unscaled) |

### Adjustment factors

- **Bodyweight factor** (push-ups and squats only): `(reference_weight / actual_weight) ^ 0.5`, clamped to [0.6, 1.5]. Heavier bodies move more mass per rep, so the rep threshold scales down moderately — not linearly — with weight.
- **Age factor** (all markers): `1.0` for age ≤ 40, then **−5% per decade past 40**, floored at `0.5`. Based on real age-decline curve data for bodyweight squats (flat 25–40, ~−7% at 45, ~−18% at 50, accelerating further past 60).

### Scoring

Each marker scores against its own beginner/intermediate/advanced band (after adjustment). Scores sum across markers with point thresholds mapping the total to an overall level (exact point values TBD at implementation — this was agreed in principle, not finalized to specific integers).

## Schema Design

Reconciled against what already exists — extend where a home already exists, create new only where nothing does.

### New: `user_profile` (one document per user)
```
user_id: str
date_of_birth: str          # ISO date — never store age directly, always derive
gender: Literal["male", "female"]
height: { value: float, unit: Literal["cm", "in"] }
weight_unit_preference: Literal["kg", "lb"]
experience_level: Optional[Literal["beginner", "intermediate", "advanced"]]  # mirrored from latest baseline_assessment, for fast lookup
created_at, updated_at
```

### New: `baseline_assessment` (append-only, one doc per assessment event)
```
user_id: str
answers: dict                # raw questionnaire responses, kept flexible — question set may evolve
experience_level: Literal["beginner", "intermediate", "advanced"]
assessed_at: datetime
```
This is the source of truth; `user_profile.experience_level` is a denormalized mirror kept in sync on every write (single write path — no independent update to the profile field elsewhere).

### Extended: `metrics` (existing collection — reused, not duplicated)
Add optional `height` and `blood_pressure: { systolic: int, diastolic: int }` fields to the existing log-entry shape already used for weight.

### Explicitly not touched in v1.8
- `checkins` injury field (stays flat/ephemeral/LLM-driven)
- `checkins` beverage tracking (stays as-is)

## Implementation Phases (planned breakdown, discovery-first per file)

1. **Schema + persistence layer** — `user_profile`, `baseline_assessment` collections/tools; extend `metrics`. No UI, no calculation logic yet.
2. **Baseline-level calculator module** — implements the formula above as a standalone, testable function.
3. **Onboarding UI** — new blocking Streamlit screen; gates on `has_user_profile()` and the (TBD) inactivity check.
4. **Wiring** — `calculate_volume_target` reads `experience_level` from the stored profile instead of an LLM-guessed parameter; remove/retire the three independent default-to-beginner fallbacks once the stored value is authoritative.

## Open Questions / Deferred Items

- Exact scoring-to-level point thresholds (sum-of-marker-scores mapping) — agreed in principle, not finalized to specific numbers yet.
- Exact "3+ months inactive" query implementation (which timestamp source, how "last active" is defined) — deferred to implementation time.
- Structured/persistent injury tracking (replacing the current flat daily-overwrite `checkins` field with something that has body-part tags, severity, and resolution) — explicitly out of scope for v1.8, flagged as a future item.
- Whether running and frequency thresholds should eventually also be demographic-scaled (currently left unisex/unscaled per explicit decision during design).
