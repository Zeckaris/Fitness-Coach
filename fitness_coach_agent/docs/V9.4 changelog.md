# V9.4 Changelog — Proactive Unattended Plan Generation
 
**Status:** Implemented, tested, working
**Depends on:** V9.1, V9.2, V9.3
 
## What this version does
 
A GitHub Actions scheduled job now generates plans automatically, without
a user needing to ask. It loops over every user, checks their planning
state, and calls the same V9.3 backfill logic Streamlit already uses —
just triggered by a timer instead of a chat message.
 
## New files
 
- **`.github/workflows/scheduled-plan-generation.yml`** — daily cron job
  (plus manual trigger for testing). Runs the script below with Mongo/
  Astra/Gemini credentials from GitHub secrets.
- **`scripts/scheduled_plan_generation.py`** — loops over all users.
  For each one: checks eligibility, auto-starts a new month's goal if
  needed, then calls `generate_today_plan()`. One user's failure never
  blocks the rest.
- **`utils/goal_performance.py`** — looks at last month's actual
  results (completion %, backlog) and decides: increase, hold, or
  decrease next month's targets.
- **`utils/goal_progression.py`** — builds the new month's goal based on
  that decision. Small changes only (+-10%), never a big jump.
- **`tests/seed_goal_progression_fixtures.py`** — throwaway test data
  generator, not part of the real app.
## Changed files
 
- **`auth/user_store.py`** — added a way to list all user IDs.
- **`tools/month_plans.py`** — added a few read-only checks: does this
  user have a goal this month, have they ever had one, what was their
  last one.
## Eligibility logic
 
1. **Has a goal this month already** -> just fill in today's plan.
2. **Had goals before, none this month** -> auto-start a new month's
   goal (scaled from last month's performance), then fill in today.
3. **Never had a goal** -> skip, do nothing.
## Bugs found and fixed
 
- New goal's targets were assuming the user hit last month's numbers
  even when they hadn't. Fixed to use their real last-logged progress
  instead, and only assume success when performance was actually good.
- Test data was missing a required field, causing one test user to
  fail -- confirmed the per-user error handling worked as intended
  (other users still processed fine).
