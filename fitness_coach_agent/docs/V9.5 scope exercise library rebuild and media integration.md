# V9.5 — Exercise Library Rebuild & Media Integration: Scope Document

**Status:** Scope (pre-design)
**Depends on:** none functionally — `workouts.json` is read directly by
`tools/workout_library.py` with no RAG/vectorstore indexing and no other
V9.x version's data shape.
**Blocks:** none currently planned. Sets up a real exercise identity
(dataset-sourced `id`/`name`) that a later structured-UI version could
render against, but no such version is currently scoped.

---

## Problem Statement

The current `data/workouts.json` (~85–100 entries) was built up piecemeal
across earlier versions, partly with names extracted from RAG documents.
A meaningful portion of those names are descriptive labels rather than
real, canonical exercise names — e.g. `"Modified Push-Up"`, which doesn't
correspond to any single standard movement (it could mean an incline,
knee, or wall push-up depending on the actual setup described). Because
the name itself doesn't encode which variant is meant, no matching
process — fuzzy string matching or otherwise — can recover the correct
canonical name from it after the fact; only the free-text `description`
field hints at it, inconsistently.

Separately, `workouts.json` currently has no visual reference (image or
GIF) for any exercise — users get text-only descriptions.

The decision made in discussion: rather than attempt to repair or
fuzzy-match the existing ~85–100 entries against an external exercise
dataset, replace the library outright with a smaller (~40 exercise),
deliberately curated set, authored directly from real entries in a
licensed exercise dataset. Because curation happens by selecting real
dataset entries rather than inventing names, canonical naming and media
attachment happen in the same step — there is no separate matching
problem to solve afterward.

## Data Source

**Chosen dataset:** [hasaneyldrm/exercises-dataset](https://github.com/hasaneyldrm/exercises-dataset)
— 1,324 exercises with per-exercise `name`, `category`, `body_part`,
`equipment`, `target`, `muscle_group`, `secondary_muscles`,
`instructions` (multi-language), `image` (180×180 thumbnail), and
`gif_url` (animation GIF).

**Licensing, confirmed:**
- Dataset structure, metadata fields, and instruction text: MIT.
- Media (images/GIFs): © Gym visual, redistributed in this repo under
  permission at 180×180 resolution, with attribution
  (`"© Gym visual — https://gymvisual.com/"`) required to stay intact.
  This is a separate license from the MIT-covered data — displaying the
  existing 180×180 assets with attribution is covered; anything beyond
  that (higher resolution, redistribution/modification of the media
  itself) would need separate clearance from Gym visual and is not
  assumed in this scope.

**Equipment coverage relevant to this app:** Body Weight is the dataset's
single largest equipment category (325 of 1,324, ~25%), followed by
Dumbbell (294), Cable (157), Barbell (154). Coverage for `none` and
`dumbbells` equipment values is not a concern; `bench`, `resistance_band`,
and `kettlebell` have smaller but workable representation (Stability
Ball, Band, Kettlebell categories, plus bench-assisted bodyweight
variants tagged under Body Weight).

## Controlled Vocabulary Changes

The existing `Equipment`, `Difficulty`, and `RequiredSpace` Pydantic
`Literal` types in `tools/workout_library.py` change as follows. These
are not purely additive — some existing values are removed or
reinterpreted, which affects the schema the LLM tool-calling agent sees.

| Field | Before | After |
|---|---|---|
| `Equipment` | `none`, `dumbbells`, `chair` | `none`, `dumbbells`, `bench`, `resistance_band`, `kettlebell` (`chair` renamed/replaced by `bench`) |
| `Difficulty` | `beginner`, `intermediate` | `beginner`, `intermediate`, `advanced` |
| `RequiredSpace` | `minimal` (single value — currently a no-op filter) | `indoor`, `outdoor` — **semantic redefinition**, not an extension. Previously answered "how much room does this need," now answers "where can this be done." |
| `TargetArea` | 14-item list (`abs`, `back`, `biceps`, `calves`, `chest`, `forearms`, `glutes`, `hamstrings`, `lower_back`, `quads`, `shoulders`, `triceps`, `full_body`, `core`) | unchanged |

## In Scope

- Replacing `data/workouts.json` in full with a newly curated set of
  approximately 40 exercises (~3 per target area across the existing
  14-item `TargetArea` vocabulary), preserving the existing JSON record
  structure and field set (`id`, `name`, `type`, `primary_target_area`,
  `secondary_target_areas`, `movement_patterns`, `equipment`,
  `required_space`, `difficulty`, `duration_minutes`, `avoid_if_injured`,
  `description`, `tags`), plus new media fields per record (`gif_url`,
  `image`, `media_id`, `attribution`, sourced directly from the matched
  dataset entry at authoring time).
- Each curated entry authored from a real, named entry in the
  exercises-dataset — canonical `name` taken from (or clearly derived
  from) the dataset entry, `description` seeded from its `instructions.en`
  and adapted to the app's existing tone/format, custom fields
  (`primary_target_area`, `movement_patterns`, `avoid_if_injured`,
  `difficulty`, `duration_minutes`, `tags`, `required_space`) authored
  against this project's vocabulary as before.
- Unique `id` per new entry, following the existing
  `{target_area}_{number}` convention (or documented replacement if
  changed during design).
- Updating `tools/workout_library.py`'s `Equipment`, `Difficulty`, and
  `RequiredSpace` `Literal` definitions and the `WorkoutQuery` field
  descriptions to match the new controlled vocabulary.
- Auditing other locations in the codebase that reference these
  vocabularies (prompts, other tools, plan generation logic) and updating
  any that assume the old value sets (e.g. `"chair"`, `"minimal"`,
  two-tier difficulty).
- Retaining the Gym visual attribution string on every curated record
  that includes media, per license terms.

## Out of Scope

- Any change to `search_workout_library`'s filtering logic
  (`_matches`), result formatting, or the `matches[:5]` cap — this
  version changes the data and the vocabulary it's filtered against,
  not the filtering mechanism itself.
- Any UI change to *display* the new `gif_url`/`image` fields — this
  version only concerns the data existing with media references attached,
  not how/whether the Streamlit app renders them. (Previously discussed
  as a possible "structured UI" version; not committed to or scoped here.)
- Expanding equipment vocabulary further toward gym-machine equipment
  (cable, barbell, Smith machine, leverage machine) — the chosen set is
  scoped to realistic home-fitness equipment.
- Multi-language exercise instructions — the dataset provides 10
  languages; this version only uses English.
- Any change to non-strength/warmup/mobility record types beyond what's
  needed to reach ~40 curated entries with the new fields.
- Retroactive backfill of media onto any already-generated user plan
  data (past plans reference exercises by name/id as they existed at
  generation time; this version does not attempt to reconcile historical
  plan records against the new library).

## Open Items for Design Phase

- Exact selection list: which ~3 exercises per target area, and final
  confirmation of dataset source names/ids to pull from.
- Whether `id` naming convention changes at all, or stays
  `{target_area}_{number}` as today.
- Full audit results: which other files reference the old `Equipment` /
  `Difficulty` / `RequiredSpace` values and need updating (`prompts.py`,
  `agent/plan_generation.py`, and any others — not yet confirmed).
- Exact field name and placement for the newly added media fields on
  each record (flat on the exercise object vs. a nested `media: {...}`
  sub-object).
- Whether `movement_patterns` values need any adjustment given the new
  entries may introduce patterns not currently represented (e.g. band-
  or kettlebell-specific movements).
- Confirming Gym visual attribution display requirements are satisfied
  by storing the attribution string in data (vs. any additional
  requirement to render it visibly wherever the media appears, which
  would be a UI-version concern but worth confirming the license terms
  don't require it at the data layer too).
