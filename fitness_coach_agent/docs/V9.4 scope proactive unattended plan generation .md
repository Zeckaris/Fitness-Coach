# V9.4 — Proactive Unattended Plan Generation: Scope Document
 
**Status:** Scope (pre-design)
**Depends on:** V9.1 (multi-user auth), V9.2 (error handling), V9.3 (backfill logic — `generate_today_plan`, `build_week_blocks`, `default_theme_path`)
**Blocks:** none currently planned; a future notification version (Telegram/email/etc.) would build on top of this
 
---
 
## Problem Statement
 
V9.3 solved *reactive* backfill: if a user opens the app and asks about
today's workout with no plan in place, the coach reconstructs whatever's
missing and generates it, in-conversation, on request. That still requires
the user to show up and ask.
 
The goal of V9.4 is to remove the "ask" step entirely for plan generation
specifically. A scheduled, unattended process should run independently of
whether anyone opens the app, and by the time any user does open it (or
whenever they next check), their data for today should already exist —
generated the same way it always has been, just without a human triggering
it.
 
This is explicitly **not** about notifying the user (a later version's
concern) and **not** about a single global "generate one plan" job — the
app is multi-user (V9.1), and users are in meaningfully different states
with respect to their own planning history. The scheduler has to reason
about each user individually.
 
## Why Not Reuse Streamlit Itself as the Scheduler
 
The app currently runs on Streamlit Community Cloud (locally for dev;
production deployment still pending). Community Cloud apps sleep when
idle, so nothing is reliably alive to host an in-process scheduler
(APScheduler or similar) — there's no guarantee the process exists at the
moment the schedule should fire. This also front-loads a decision that
would matter regardless: the generation logic (`agent/`, `tools/` modules)
already doesn't depend on Streamlit at all — it talks directly to Mongo,
AstraDB, and Gemini. Streamlit is just one caller among what will
eventually be several (a Flutter client is planned long-term). The
scheduler should be another independent caller of that same logic, not
something bolted onto the UI process.
 
**Chosen mechanism:** a GitHub Actions scheduled workflow (`on: schedule`,
cron syntax). A script checked into the repo imports the existing
`agent`/`tools` modules directly, connects to Mongo/AstraDB using
credentials from repo secrets, does the work, and exits. No new hosting,
no AWS account/IAM to set up, minute-level cron precision isn't needed for
a daily trigger. This can be swapped for Lambda + EventBridge later if
finer-grained scheduling is ever needed, without touching the generation
logic itself.
 
## Per-User Eligibility
 
Because users differ in planning history, the scheduler needs an
eligibility check per user, not a blanket "generate for everyone":
 
1. **Never set a monthly goal, ever (any month, past or present).**
   No signal this user is engaged with the planning feature at all.
   **Skip entirely** — generating a plan for someone who's never
   expressed a goal would be inventing intent they never gave.
2. **Has a monthly goal for the current month already, week structure
   exists, today's plan is missing.** This is exactly V9.3's backfill
   case. **Run it** — reuse the existing chain.
3. **Has set monthly goals before, but none for the current month.**
   The scheduler **auto-starts a new month's goal** on the user's behalf,
   carrying forward from their most recent goal with **some automatic
   progression applied** (e.g. a slight volume increase) rather than an
   unchanged copy — exact progression logic is a design-phase decision,
   not a scope-phase one. Once the new goal exists, the rest of the chain
   (week blocks → today's plan → forward window) proceeds the same as
   case 2.
In all eligible cases, the end state is the same as V9.3's: today's plan
and the forward tomorrow/day+2/day+3 window exist, generated through the
same validated logic as any normal plan — structurally indistinguishable
from a manually- or conversationally-triggered one.
 
## In Scope
 
- A standalone script, independent of the Streamlit process, invocable by
  a GitHub Actions scheduled workflow, that connects directly to
  Mongo/AstraDB and calls the existing generation logic.
- Iterating over all users and classifying each into one of the three
  eligibility cases above.
- For eligible users, running whatever subset of the reconstruction chain
  (new month goal → week blocks → today's plan → forward window) is
  missing — reusing V9.3's and V9.2's logic and guarantees (create-only
  protection for today, retry/re-prompt machinery, partial-failure
  "keep what succeeded" behavior) rather than parallel bespoke logic.
- Auto-starting a new month's goal for case 3 users, with some automatic
  progression from their prior goal (exact formula deferred to design).
- Per-user failure isolation: one user's failure (Mongo hiccup, LLM
  failure after retries, etc.) must not block processing of other users
  in the same scheduled run.
## Out of Scope
 
- Any notification or delivery channel (Telegram, email, push, or
  otherwise) telling the user their plan is ready. V9.4 ends at "the data
  exists in Mongo, ready to be read normally through the existing app
  flow." Notification is a later version's concern.
- Any change to the "never rewrite an existing day" protection, or to
  `update_three_day_plan`'s refusal of `date == today` — unchanged from
  V9.3.
- Retroactive generation for days that have already passed — still not
  meaningful to backfill, same as V9.3's position.
- A Flutter client or any change to how any existing client (Streamlit)
  reads/displays this data — this version only concerns data existing,
  not how it's presented.
- AWS Lambda/EventBridge or any infra beyond GitHub Actions — noted as a
  possible future swap, not built now.
## Open Items for Design Phase
 
- Exact algorithm for the case-3 "automatic progression" applied to a
  newly auto-started monthly goal (which dimension(s) change, by how
  much, any caps or limits).
- How the "has this user ever set a monthly goal" check is queried —
  distinct from V9.3's `has_theme_path_for_current_month`, which is
  scoped to the current month only; this needs an any-month existence
  check.
- Whether the per-user work is orchestrated by directly composing
  existing plain functions (`build_week_blocks`, `default_theme_path`,
  etc., following V9.3's no-nested-`@tool`/`@mongo_guarded` precedent) or
  needs a new orchestration layer — deferred to design now that scope
  doesn't assume a specific call shape.
- Schedule frequency and time-of-day for the GitHub Actions cron trigger.
- Idempotency under an overlapping or double-fired run — V9.3's
  existence-checks-before-writing pattern likely already covers this,
  but worth confirming explicitly rather than assuming.
- Secrets management for Mongo/AstraDB/Gemini credentials inside GitHub
  Actions (repo secrets vs. environment-level secrets).
