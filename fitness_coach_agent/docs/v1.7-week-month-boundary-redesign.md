# v1.7 — Calendar-Aligned Week Boundaries and Theme-Path Fallback Redesign

**Status:** Design / Pre-implementation — awaiting explicit approval before any code changes.
**Branch:** dev
**Authors:** Engineering
**Date:** 2026-09-03

---

## Background and Motivation

v1.6.0 introduced full 7-day, Sunday-anchored week plans with periodized week themes
(`WeekThemeEnum`) and a volume-weight matrix (`THEME_WEIGHT_MATRIX`). A subsequent
production investigation uncovered two compounding bugs that corrupt volume-target
arithmetic under foreseeable real-world conditions. This document describes both
problems in detail, proposes fixes, and lists every file that requires change.

---

## Problem 1 - Week/Month Boundary Mismatch Creates Phantom Week Numbers

### 1.1 Root Cause

The system uses **three independent date anchors** that were never designed to agree:

| Anchor | Derived from | Location |
|---|---|---|
| `month_id` | `datetime.now(LOCAL_TZ)` at call-time | `_current_month_id()` in every file |
| `week_id` | Sunday of the week containing the date | `_get_week_id_for_date()` in `tools/week_plans.py` |
| `week_number` | Day offset from the 1st of the **week's** month | `_get_week_number_from_date()` in `tools/week_plans.py` |

A Sunday-anchored week can straddle two calendar months. When today falls early in a
new month but the active week started in the prior month, the three anchors diverge:

- `month_id` -> current calendar month (correct for the user's goal)
- `week_id` -> prior-month Sunday (correct for the stored week document)
- `week_number` -> position of that Sunday **within its own month** (prior month)

### 1.2 Confirmed Failure Scenario

**Concrete example (Sep 2-3, 2026):**

1. Goal confirmed on Sep 2-3, 2026.
2. Active week: `week_id = "2026-08-30"` (Sunday Aug 30).
3. `_get_week_number_from_date("2026-08-30")` evaluates as **Week 5 of August**.
4. `_current_month_id()` returns `"2026-09"` (September).
5. `update_week_plan` fetches the September month doc and looks for `week_number == 5`.
6. If September path has 5 entries, Week 5 is typically **Deload** (weight `0.60`).
7. `_calculate_week_targets()` filters `remaining_theme_weights` where `week_number >= 5`.
   If only week 5 matches: `sum_remaining_weights = 0.60`, `theme_fraction = 1.0`.
8. **Result:** 100% of the month remaining volume target assigned to a single Deload week.

### 1.3 Broader Risks Identified

**A. Split-month volume credit.** Workouts on Aug 30-31 are credited to August's goal;
Sep 1-2 to September's. A single week spanning the boundary splits credit across two
month goals.

**B. Invisible history in remaining-volume math.** `_calculate_week_targets()` queries
by `"date": {"$regex": f"^{month_id}"}`. Completed sets from Aug 30-31 carry the
"2026-08-" prefix and are invisible to September's `completed_so_far` counter.

**C. Silent theme fallback on week-number mismatch.** When the wrong `week_number` is
applied to the wrong month's `week_plan_path`, the `next(..., "Foundation")` sentinel
in `update_week_plan` and `next(..., "Volume")` in `generate_today_plan` fire silently.

**D. Backlog carry-over across month boundaries.** `sync_backlog()` sweeps all past
planned days without filtering by month. A deficit from Aug 30 is reinserted into
September sessions, potentially inflating September's per-session target quantity.

## Problem 2 - Theme-Path Fallback Is Silent and Architecturally Inconsistent

### 2.1 The Happy Path

`generate_theme_path()` in `agent/monthly_review.py` calls the LLM with
`THEME_PATH_PROMPT`. The LLM returns a `ThemePathOutput` containing exactly
`total_weeks` `WeekThemeOutput` entries written to `week_plan_path`.

### 2.2 The Trapdoor

Two failure conditions silently replace LLM output with a hardcoded default:

```python
# agent/monthly_review.py lines 148-160
if len(themes) != total_weeks:
    logger.warning("Theme path generation returned %d themes, expected %d ...", ...)
    return default_theme_path(total_weeks)

except StructuredOutputFailed:
    logger.exception(...)
    return default_theme_path(total_weeks)
```

`default_theme_path` cycles through `["Volume", "Intensity", "Volume", "Peak", "Deload"]`.

### 2.3 Specific Problems

**A. Foundation is omitted.** The fallback chain never includes `"Foundation"`, which
is inconsistent: `THEME_WEIGHT_MATRIX` defines Foundation as the weight-1.00 baseline.

**B. No personalization.** The fallback ignores experience_level, backlog size, prior
adherence, and goal type. A new user and advanced user receive identical sequences.

**C. No observability.** Nothing records whether the theme path was LLM-generated or
fell back. Post-hoc debugging cannot distinguish the two cases.

**D. Weak validation on LLM output.** `WeekThemeOutput` has no `ge=1, le=total_weeks`
constraint on `week_number`. An LLM emitting duplicate week numbers (e.g. two entries
with `week_number: 1`) passes the coarse length check.

**E. Redundant fallback in `generate_today_plan`.** Lines 458-464 in `tools/plans.py`
independently write a `default_theme_path` when no theme path exists, without any
source flag. Two code paths can silently write incompatible fallback paths.

### 2.4 Interaction with Problem 1

When Problem 1 produces a wrong `week_number` that does not match any entry in the
month's `week_plan_path`, `next(..., "Foundation")` fires silently. Then
`_calculate_week_targets` looks up Foundation's weight but filters
`remaining_theme_weights` against the wrong baseline — compounding the volume error.
Without observability on either failure, root-cause analysis is extremely difficult.

## Proposed Design

### Section 1 - Calendar-Aligned Week Model

#### 1.1 Canonical Week Boundary Algorithm

Replace all Sunday-anchored logic with a **month-contained week** model:

```
Given a month M (year, month number):

  month_start = date(year, month, 1)
  month_end   = last day of M

  Week 1: month_start through first Saturday on-or-after month_start
  Middle weeks: full Sunday-Saturday spans, entirely within M
  Last week: Sunday-after-last-full-week through month_end

Merge rule:
  If week 1 has 1 or 2 days -> merge into week 2
  If last week has 1 or 2 days -> merge into the preceding week
  Result: all weeks are 3-9 days. Middle weeks are always 7 days.
```

**Worked examples:**

| Month | Day 1 | Week 1 | Last Week | Total Weeks |
|---|---|---|---|---|
| Sep 2026 | Tuesday | Sep 1-5 (5d) | Sep 27-30 (4d) | 5 |
| Oct 2026 | Thursday | Oct 1-3 (3d) | Oct 25-31 (7d) | 5 |
| Nov 2026 | Sunday | Nov 1 (1d) -> merged | Nov 29-30 (2d) -> merged | 4 |
| Feb 2026 | Sunday | Feb 1 (1d) -> merged | Feb 22-28 (7d) | 4 |
| Mar 2026 | Sunday | Mar 1 (1d) -> merged | Mar 29-31 (3d) | 5 |

**Key invariants:**

1. Every day in a month belongs to exactly one week of that month.
2. No week spans two calendar months.
3. Every week is 3-9 days long.
4. `week_id` is the first calendar day of the week (may not be a Sunday).
5. `week_number` is 1-indexed, derived from position in the month week list.
6. `month_id` is always the calendar month that owns the week.

#### 1.2 Single Source of Truth - `compute_month_weeks(month_id)`

All date arithmetic should flow from a single new canonical function:

```python
def compute_month_weeks(month_id: str) -> list[dict]:
    """
    Returns an ordered list of week descriptors for the given month.
    Each descriptor:
      {
        "week_number": int,   # 1-indexed
        "start_date":  str,   # YYYY-MM-DD (first day of this week within the month)
        "end_date":    str,   # YYYY-MM-DD (last day of this week within the month)
        "day_count":   int,   # number of calendar days in this week
      }
    Merge rule applied: no entry has day_count < 3.
    """
```

**Proposed home:** `utils/calendar_weeks.py` (new file). Pure, deterministic, I/O-free.
Every other file that currently calculates week boundaries should import and call this.

**Derived helpers from the same module:**

```python
def get_week_for_date(date_str: str) -> dict:
    """Returns the week descriptor containing date_str, or raises ValueError."""

def weeks_in_month(month_id: str) -> int:
    """Equivalent to len(compute_month_weeks(month_id))."""

def month_id_for_date(date_str: str) -> str:
    """Canonical month_id for a specific date. Replaces call-time _current_month_id()."""
```

#### 1.3 Derived Identifiers - Single Chain

```
month_id    = month_id_for_date(date_str)
week        = get_week_for_date(date_str)
week_id     = week["start_date"]       # first day of week, not necessarily Sunday
week_number = week["week_number"]      # position in month week list
```

Every call site currently using `_get_week_id_for_date()` or
`_get_week_number_from_date()` must be updated to derive from `get_week_for_date()`.

#### 1.4 Variable Week Length in Volume Math

`_calculate_week_targets()` hardcodes `sessions_per_week = 4`. With 3-9 day weeks:

```
sessions_in_week = max(1, round(4 * day_count / 7))
daily_target = week_target / sessions_in_week
```

See Open Question Q1 for the alternative fixed-4-sessions approach.

### Section 3 - Theme-Path Fallback Redesign

#### 3.1 Make Fallbacks Visible - `theme_path_source` Field

Add `theme_path_source` to the month document whenever `week_plan_path` is written:

```json
{
  "week_plan_path": [...],
  "theme_path_source": "llm | fallback_length_mismatch | fallback_parse_failure | manual_recovery"
}
```

Write path assignments:
- `generate_theme_path()` happy path -> `"llm"`
- `generate_theme_path()` length mismatch branch -> `"fallback_length_mismatch"`
- `generate_theme_path()` `StructuredOutputFailed` branch -> `"fallback_parse_failure"`
- `generate_today_plan()` bootstrap step -> `"fallback_parse_failure"`
- `_refresh_week_themes_impl()` (user-triggered) -> `"manual_recovery"`

The dashboard (`render_month_goal()`) should surface an amber indicator when
`theme_path_source != "llm"`: "Week themes were set by default — click Set Week Themes
to regenerate."

#### 3.2 Upgrade `WeekThemeOutput` Validation

```python
class WeekThemeOutput(BaseModel):
    week_number: int = Field(ge=1)   # lower bound; caller checks upper bound
    theme: WeekThemeEnum

class ThemePathOutput(BaseModel):
    week_plan_path: List[WeekThemeOutput]

    @model_validator(mode="after")
    def validate_week_numbers(self) -> "ThemePathOutput":
        nums = [w.week_number for w in self.week_plan_path]
        if len(set(nums)) != len(nums):
            raise ValueError(f"Duplicate week_number values: {nums}")
        return self
```

This catches "correct count but duplicate week numbers" — a case the existing
`len(themes) != total_weeks` guard misses.

#### 3.3 Fallback Chain Options

**Option A - Keep existing:** `["Volume", "Intensity", "Volume", "Peak", "Deload"]`
Foundation still absent. Adds only observability and validation.

**Option B (Recommended):** `["Foundation", "Volume", "Intensity", "Peak", "Deload"]`
- Includes Foundation as the first week (consistent with V1.6.2 periodization baseline)
- Follows a coherent arc for any month length
- For <5 weeks: truncate from right (drop Deload, then Peak)
- For >5 weeks: cycle

**Option C - No fallback, raise visibly:** Breaks unattended operation. Defer until
scheduler error-handling is more mature.

#### 3.4 Consolidate the Two Independent Fallback Write Paths

`generate_theme_path()` and `generate_today_plan()` each independently write
`default_theme_path` — no coordination, no source flag.

**Proposed fix:**

1. If no theme path exists in `generate_today_plan()`, call `_refresh_week_themes_impl()`
   first (which already wraps `generate_theme_path()` and can write with the correct flag).
2. Only if that fails (LLM unavailable) should `generate_today_plan()` write the
   `default_theme_path` directly, always setting `theme_path_source`.

This centralizes theme-path generation and eliminates the race condition.

#### 3.5 Prompt Update for Variable Week Count

`THEME_PATH_PROMPT` should include week descriptors so the LLM can account for short
boundary weeks when choosing themes:

```
This month has {total_weeks} weeks:
  Week 1: {start} - {end} ({day_count} days)
  Week 2: {start} - {end} (7 days)
  ...
  Week N: {start} - {end} ({day_count} days)

For boundary weeks with 3-4 days, prefer Foundation or Deload.
Avoid Peak or Volume for very short weeks.
```

### Section 6 - Additional Issues Flagged During Analysis

#### 6.1 `_current_month_id()` Defined Four Times

The one-liner `datetime.now(LOCAL_TZ).date().strftime("%Y-%m")` appears in:
- `tools/week_plans.py` line 21
- `tools/month_plans.py` line 57
- `tools/plans.py` line 81
- `tools/progress.py` line 18

Any per-date operation needing the month of a specific date must use
`month_id_for_date(date_str)`. The proposed `utils/calendar_weeks.py` should also
export a shared `current_month_id()` for callers that genuinely mean today's month.

#### 6.2 `_find_week_doc_for_date()` Fallback Is Unsafe

```python
def _find_week_doc_for_date(date_str: str) -> Optional[dict]:
    doc = collection.find_one({"user_id": ..., "daily_volume_targets.date": date_str})
    if doc:
        return doc
    return collection.find_one({"user_id": ...}, sort=[("week_id", -1)])  # ANY latest week
```

When no exact match exists, this returns the most recent week doc regardless of
relevance. `get_week_focus_for_date()` and `get_daily_volume_targets_for_date()` could
silently return targets from a completely unrelated week.

**Recommend removing the fallback `find_one` and returning `None` unconditionally
when no exact match is found.** See Open Question Q3.

#### 6.3 `goal_context_node` Uses Tomorrow for Week Focus

```python
# agent/graph.py line 123
tomorrow = (datetime.now(LOCAL_TZ) + timedelta(days=1)).strftime("%Y-%m-%d")
week_focus = get_week_focus_for_date(tomorrow)
```

If tomorrow falls in a new month's week this query could miss the focus. After the
redesign `get_week_focus_for_date` will look up the correct month-contained week
automatically. Flag as a key call site to verify during testing.

#### 6.4 `calculate_volume_target` Passes Wrong `weeks_in_month`

In `tools/month_plans.py` line 160:

```python
weeks_in_month=_weeks_in_month(_current_month_id()),
```

Uses today's month, not the goal's month. Almost always correct, but could be wrong
during a month-rollover session. Fix with explicit `month_id` parameterization.

## Open Questions for Review

> [!IMPORTANT]
> **Q1 - Session count scaling for variable week lengths:**
> Proposed: `sessions_in_week = max(1, round(4 * day_count / 7))` giving
> 3d->2 sessions, 5d->3, 7d->4, 9d->5.
> Alternative: always 4 sessions with `daily_target = week_target / 4`
> (consistent dosing but some days in short weeks get 0 targets). Which do you prefer?

> [!IMPORTANT]
> **Q2 - Fallback chain: Option B or another option?**
> Proposed: `["Foundation", "Volume", "Intensity", "Peak", "Deload"]` replacing
> `["Volume", "Intensity", "Volume", "Peak", "Deload"]`.
> Foundation added; Volume deduplicated. Keep Foundation out of fallback or include it?

> [!IMPORTANT]
> **Q3 - Remove `_find_week_doc_for_date()` unsafe fallback in v1.7 or defer?**
> The fallback (return most recent week doc on no match) is independently dangerous
> but unrelated to the boundary bug. Fix in this PR or a separate one?

> [!IMPORTANT]
> **Q4 - Tighten `WeekThemeInput.theme` to `WeekThemeEnum` in v1.7 or defer?**
> Currently raw `str` in `tools/month_plans.py` vs typed `WeekThemeEnum` in
> `agent/monthly_review.py`. Unifying is clean but touches every call site.

> [!IMPORTANT]
> **Q5 - `theme_path_source` display in dashboard:**
> Proposed amber badge in `render_month_goal()` when not `"llm"`.
> Right place, or should it be more prominent / logged-only for now?

> [!NOTE]
> **Q6 - Store `day_count` in `week_plans` documents?**
> Explicit storage makes downstream math self-contained but is denormalized
> (derivable from `start_date`/`end_date`). Store explicitly or derive on demand?
