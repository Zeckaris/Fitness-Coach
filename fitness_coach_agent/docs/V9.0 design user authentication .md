# V9.0 — User Authentication: Design Document
 
**Status:** Design (pre-implementation)
**Git tag target:** `v1.1.0`
**Depends on:** none
**Blocks:** V9.1 (error handling), V9.2 (backfill logic), and all subsequent V9.x versions
 
---
 
## Problem Statement
 
The application currently operates against a single hardcoded identity
(`DEFAULT_USER_ID = "default_user"`), duplicated independently in
`tools/plans.py` and `agent/monthly_review.py`. All Mongo reads/writes across
`tools/`, `app/streamlit_app.py`, and `agent/monthly_review.py` resolve to
this shared value regardless of who is using the deployed app, meaning any
two concurrent users read and overwrite the same documents. This must be
resolved before meaningful multi-user testing of any subsequent V9.x version.
 
## Non-Goals
 
- No OAuth, JWT, or third-party identity provider.
- No separate backend/API service or auth framework.
- No change to `thread_id` behavior. Confirmed by design: each session
  intentionally starts a fresh conversation thread (no chat continuity),
  while Mongo-persisted data (check-ins, plans, goals) remains continuous
  per user. This is existing, correct behavior and out of scope here.
## Architecture
 
### 1. New `users` collection (MongoDB)
 
Fields: `username` (unique index), `password_hash` (bcrypt, salted),
`created_at`.
 
### 2. New `auth/` package
 
Sibling to `agent/`, `app/`, `db/`, `rag/`, `tools/`:
 
- `auth/user_store.py` — `create_user(username, password)`,
  `get_user_by_username(username)`, `verify_password(user_doc, password)`.
  Talks to Mongo via the existing `db/mongo_client.py` connection getter —
  no second DB client pattern introduced.
- `auth/context.py` — a `contextvars.ContextVar`-based holder for the
  current user's ID: `set_current_user_id(user_id)`, `get_current_user_id()`.
  Chosen over a plain global because Streamlit sessions can run under
  separate threads; `ContextVar` gives per-context isolation without a
  global-state race risk.
  Chosen over adding `user_id` as a tool function parameter because
  LangChain's `@tool` decorator would expose it as an LLM-fillable
  argument — `user_id` must never be visible to or settable by the LLM.
### 3. `CoachState` — no change required
 
`user_id` is not conversation data the agent reasons over; it's an
execution-context value read internally by tool functions, not something
the graph or LLM needs to see or pass along.
 
### 4. ID scheme
 
MongoDB's own `_id` (ObjectId) on the `users` document becomes the
canonical `user_id`. It is cast to `str(user_doc["_id"])` immediately upon
login and stored as a string everywhere in application code (context var,
session state, Mongo query filters against `user_id` fields elsewhere). It
is cast back to `ObjectId(...)` only at the point of querying the `users`
collection by `_id` itself — never elsewhere.
 
### 5. Migration of existing call sites
 
From grep audit of `DEFAULT_USER_ID`:
 
- `agent/monthly_review.py` — delete its independent `DEFAULT_USER_ID`
  constant; replace all 5 usages with `get_current_user_id()`.
- `app/streamlit_app.py` — remove the `DEFAULT_USER_ID` import from
  `tools/plans.py`; replace all 14 raw Mongo query usages with
  `get_current_user_id()`.
- `tools/plans.py` — remove `DEFAULT_USER_ID` definition once nothing
  references it.
### 6. Login gate in `streamlit_app.py`
 
The entire app body (dashboard row, sidebar, tabs) renders only when
`st.session_state.get("user_id")` is set. Otherwise, render a minimal
login/register form.
 
On successful login:
```python
st.session_state["user_id"] = str(user_doc["_id"])
set_current_user_id(st.session_state["user_id"])
```
 
Because `ContextVar` state doesn't automatically persist across Streamlit
reruns the way `session_state` does, `set_current_user_id(...)` must be
called on every rerun once `st.session_state["user_id"]` is confirmed
present — not only once at login.
 
## Password Handling
 
`bcrypt`, salted (bcrypt salts automatically per call) — no additional
framework.
 
## Open Items for Implementation Phase
 
- Minimum username/password validation rules (length, allowed characters)
  — not yet decided, low-stakes, can default to simple rules unless
  otherwise specified.
- Logout behavior — clearing `st.session_state["user_id"]` and re-gating
  the app; straightforward, no design risk.
