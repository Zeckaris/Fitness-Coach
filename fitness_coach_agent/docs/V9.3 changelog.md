# V9.3 Changelog — Backfill Logic for Off-Cadence Planning
 
**Status:** Implemented, tested, working
**Depends on:** V9.2 (`call_structured_llm_with_reprompt`, `@mongo_guarded`, `agent/error_handling.py`)
**Related docs:** `V9.3 scope - backfill logic for off-cadence planning.md`, `V9.3 High-Level Design.md`, `V9.3 Design Addendum` (folded into this changelog — no separate addendum file was kept)

## What this version does
 
Previously, if a user asked about today's workout and no plan document existed for
today (either because they were starting fresh mid-month, or returning after a
gap), the agent had no way to fix this in-conversation. `get_today_workout_status`
would report `"no_plan"` and stop; the only path forward was a manual Streamlit
button that only set the month's theme path, not the week's actual structure —
the user then had to ask again.
 
V9.3 adds a single new tool, `generate_today_plan`, that the coach LLM calls
automatically whenever `get_today_workout_status` returns `"no_plan"`. It
reconstructs whatever upstream state is missing (month theme path, week block
structure) and generates today's actual plan plus the forward tomorrow/day+2/
day+3 window, all in the same turn — so the user asks once and gets a real,
persisted plan, with no manual steps.
 
`update_three_day_plan` itself is completely untouched: still forward-only,
still categorically refuses `date == today`. The create-only guarantee (today's
plan generation only ever fires when no document exists at all) is enforced
structurally, not conditionally.

## New files
 
### `utils/__init__.py`, `utils/theme_defaults.py`
New top-level package. `default_theme_path(total_weeks)` — a pure, non-LLM
function that deterministically cycles a fallback theme chain
(`Volume → Intensity → Volume → Peak → Deload`). Used in two places:
- `generate_theme_path()`'s existing `StructuredOutputFailed` fallback in
  `agent/monthly_review.py` (previously this logic was inlined there).
- `generate_today_plan`'s month-theme-path recovery step, deliberately
  **without** an LLM call (see "Design decisions" below).
### `agent/plan_generation.py`
New file. Holds `generate_backfill_days(...)` — the one combined structured
LLM call that generates today + the forward 3-day window together. Kept
separate from `agent/monthly_review.py` since it's a different concern
(actual workout content generation, not monthly review/theme-path logic)
that happens to share the same LLM-call machinery and the project convention
that LLM-calling code lives under `agent/`.

## Changed files
 
### `tools/month_plans.py`
- Added `has_theme_path_for_current_month() -> bool`. Read-only, not
  `@mongo_guarded` (a `False` result is legitimate, same reasoning as
  `ensure_week_plan_exists`).
### `tools/week_plans.py`
- Extracted `save_week_plan(...)` as a plain function (guard + validate +
  write), with a new `require_theme_path: bool = True` parameter.
  `update_week_plan` (the `@tool`) is now a thin shell calling it.
  `require_theme_path=False` is used by `generate_today_plan`, since its
  backfill flow may have just written a theme path moments earlier in the
  same call — the button-messaging guard doesn't apply there.
- `_calculate_week_targets` (previously dead code) is now actually used, via
  `build_week_blocks` in `agent/monthly_review.py`.
### `agent/monthly_review.py`
- `generate_theme_path()`: its `StructuredOutputFailed` fallback and its
  "wrong theme count" fallback both now call `default_theme_path()` instead
  of inlining padding logic — also fixes a latent inconsistency where the two
  failure paths previously used slightly different fallback behavior.
- Added `WeekBlockOutput` (Pydantic) and `build_week_blocks(...)` — a plain
  function mirroring `generate_theme_path`'s shape: pulls hard numbers from
  `_calculate_week_targets`, makes one structured LLM call for the
  qualitative block-focus labels only (not the arithmetic).
- `refresh_week_themes` bug fix: extracted `_refresh_week_themes_impl()` as
  a plain function. The `@tool`-wrapped `refresh_week_themes` is now a thin
  shell around it. This fixes a pre-existing bug (not introduced by V9.3,
  but surfaced by it): `run_monthly_review()` was calling
  `refresh_week_themes()` as a plain function, which broke
  (`TypeError: 'StructuredTool' object is not callable`) once
  `refresh_week_themes` was made LLM-callable via `@tool`. `run_monthly_review`
  now calls `_refresh_week_themes_impl()` directly, preserving its documented
  requirement that Mongo failures propagate as real exceptions rather than
  being swallowed into a fallback string.
### `tools/plans.py`
- Added `BackfillDayPlanInput` — sibling of `DayPlanInput`, identical
  exercise-count/phase/duration validation, but permits `date == today`
  (the one deliberate carve-out). Exact date-value correctness (does this
  match one of the 4 expected dates?) is checked by `generate_today_plan`
  itself post-generation, not by the schema.
- Added `BackfillPlanOutput` — wraps `List[BackfillDayPlanInput]`, validates
  exactly 4 unique dates.
- Added `generate_today_plan()` — the main new tool. `@tool` + single
  `@mongo_guarded` (no nested guarded/tool calls anywhere inside it, see
  "Design decisions"). Sequence:
  1. Guard: confirmed month goal must exist.
  2. Guard (create-only): refuse if any document already exists for today.
  3. Month theme path: if missing, write `default_theme_path()` directly
     (no LLM call).
  4. Week block structure: if missing, call `build_week_blocks()` then
     `save_week_plan(..., require_theme_path=False)`.
  5. Gather context via existing read-only tools (`get_past_plans`,
     `get_backlog`, `search_fitness_knowledge_base`, `search_workout_library`),
     called via `.invoke()` — safe here since none of them write anything.
  6. One combined call to `generate_backfill_days()` for today + forward
     3 days. On `StructuredOutputFailed`: keep whatever succeeded in steps
     3-4, return a graceful "try again in a moment" message (see
     "Partial-failure behavior").
  7. Validate returned dates match exactly what's expected.
  8. Write all 4 days directly to `plans_collection` (not via
     `update_three_day_plan` — its schema excludes today, and nesting its
     `@tool`/`@mongo_guarded` call would be unsafe).
  9. Best-effort backlog fold: match generated exercise names against open
     backlog items, mark reinserted.
### `agent/graph.py`
- `TOOLS` list: added `generate_today_plan`, `refresh_week_themes`.
### `agent/prompts.py`
- Tool 15 (`get_today_workout_status`): on `"no_plan"`, instructs the LLM to
  call `generate_today_plan()` immediately in the same turn.
- New tool 16 (`generate_today_plan`) and tool 17 (`refresh_week_themes`)
  entries.
- New prompt constants: `WEEK_BLOCK_PROMPT`, `BACKFILL_DAY_PLAN_PROMPT`.

## Design decisions made during this version
 
1. **Month theme-path recovery is non-LLM.** Originally scoped to reuse
   `refresh_week_themes` (LLM-backed). Changed to reduce LLM-call surface
   and latency/reliability risk (multiple free-tier API keys — each
   additional chained LLM call is another failure point). Uses
   `default_theme_path()` instead. `refresh_week_themes` itself is
   unchanged and still used for its original (conversational,
   user-visible) recovery case.
2. **Today + forward window collapsed into one combined structured LLM
   call**, rather than generating today separately from the 3-day forward
   window. Reduces worst-case LLM calls inside `generate_today_plan` from
   an implicit 3-4 down to a maximum of 2 (week blocks, today+forward).
3. **No nested `@mongo_guarded` / no calling `@tool`-wrapped functions
   internally.** `@mongo_guarded` returns a string on a dependency failure
   rather than raising — calling another guarded function from inside an
   already-guarded function risks a Mongo outage silently becoming
   "valid-looking" string data written into a document. `generate_today_plan`
   only ever calls plain, undecorated functions internally and does its own
   Mongo reads/writes directly. This required extracting `save_week_plan`
   out of `update_week_plan` and `_refresh_week_themes_impl` out of
   `refresh_week_themes`.
4. **Partial-failure behavior: keep whatever succeeded.** If theme-path and
   week-block generation succeed but the today+forward-window call fails
   after retries, the theme path and week blocks are left in place (they're
   valid data) rather than rolled back. The next call to `generate_today_plan`
   only needs to retry the failed step, since each step already checks
   "does this already exist?" before running. No transaction/rollback
   machinery needed.
5. **Read-only context-gathering tools are called via `.invoke()`**
   (`get_past_plans`, `get_backlog`, `search_fitness_knowledge_base`,
   `search_workout_library`) — safe despite being `@tool`/`@mongo_guarded`/
   `@astradb_guarded`-wrapped, since a degraded result here only weakens a
   prompt, it's never written as if it were structured data.

## Bug found and fixed during testing: Gemini `response_schema` rejects
## `min_length`/`max_length` on `List[ComplexObject]`
 
During testing, `generate_today_plan` consistently failed with a bare
`400 INVALID_ARGUMENT` from Gemini, with no schema-specific detail in the
error body. Bisected via a throwaway diagnostic script
(`tests/debug_backfill_schema.py`, not part of the shipped app) by testing
progressively closer approximations of the real schema through
`with_structured_output`.
 
**Root cause confirmed:** a `List[SomeComplexPydanticModel]` field declared
with `Field(min_length=N, max_length=M)` is rejected by Gemini's
`response_schema` conversion (used by `with_structured_output`) — even
though the same object shape works fine unconstrained, and even though the
identical `min_length`/`max_length` pattern works fine on `List[str]`. This
is specific to `with_structured_output`'s response-schema path; it does not
necessarily affect LangChain's tool-calling schema path (used by
`update_three_day_plan`'s `args_schema`, which has the same
`min_length=7, max_length=20` pattern on `DayPlanInput.exercises` but goes
through a different Gemini API surface and was not confirmed to be affected).
 
**Fix applied:** removed `min_length=7, max_length=20` from
`BackfillDayPlanInput.exercises`' `Field(...)` declaration; added the same
7-20 bound as an explicit check inside the existing
`model_validator(mode="after")`. Same enforcement, checked after generation
instead of declared in the schema sent to the API.
 
**Not yet applied:** `DayPlanInput` (in the same file, used by
`update_three_day_plan`) has the identical `min_length=7, max_length=20`
pattern but goes through tool-calling, not `with_structured_output` — left
untouched since it has not been observed to throw this error. Flagged as an
open follow-up item below.

## Open items / follow-ups (not resolved in this version)
 
- **`DayPlanInput`'s `min_length`/`max_length`** may or may not carry the
  same latent risk as `BackfillDayPlanInput` did — untested, since it goes
  through a different schema-conversion path. Worth a defensive fix or at
  least a confirmed test later.
- **Backlog reconciliation is name-matching only**, not exact placement
  tracking — `BackfillDayPlanInput` has no field capturing which backlog
  item an exercise fulfills, so matching is best-effort by exercise name
  appearing anywhere in the generated 4 days.
- **No injury/avoid-body-parts context** is passed into backfill generation.
  `SYSTEM_PROMPT`'s injury rule relies on live conversation context a
  backend backfill call doesn't have. If a user has a recently logged
  injury, this path currently won't know to avoid it. Candidate for pulling
  in recent check-in context in a future version.
- **No backfilled-document marker.** The original scope doc left open
  whether backfilled plan/week docs should carry a distinguishing field
  (e.g. `"generated_via": "backfill"`) for debugging/auditing. Not added —
  documents are structurally indistinguishable from normally-generated ones.
- **`update_week_plan`'s existing (pre-V9.3) behavior still relies on the
  coach LLM doing the remaining-volume ÷ weeks ÷ 2 arithmetic itself**,
  conversationally, per tool 14's prompt instructions — `_calculate_week_targets`
  is now used by `build_week_blocks` (V9.3's backfill path) but was not
  retrofitted into `update_week_plan`'s normal path. This is a pre-existing
  gap, not introduced by V9.3, but now more visible since one path does the
  math deterministically and the other doesn't. Worth its own follow-up.
- **Even split between Block 1 and Block 2 volume targets.**
  `_calculate_week_targets` computes one `block_target` per exercise
  (week target ÷ 2), applied identically to both blocks. No logic exists
  (in this version or before it) for an uneven/progressive split across a
  week's two blocks.
