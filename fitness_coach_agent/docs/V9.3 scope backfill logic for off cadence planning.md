# V9.3 — Backfill Logic for Off-Cadence Planning: Scope Document
 
**Status:** Scope (pre-design)
**Depends on:** V9.2 (error handling — `call_structured_llm_with_reprompt`, `@mongo_guarded`)
**Blocks:** V9.5 (structured UI rendering depends on plan data reliably existing)
 
---
 
## Problem Statement
 
The agent's planning model assumes a continuous chain: month theme path →
week block structure (`week_plans`) → forward daily plans (`plans`,
tomorrow/day+2/day+3 only). Each link is only ever generated as an
extension of the previous one, on the assumption that someone is
actively using the app every few days to keep the chain moving forward.
 
That assumption breaks the moment a user is away for any stretch of time
— starting fresh mid-month, or returning after several days off. Two
concrete symptoms result today:
 
1. **No week structure for "today."** `get_today_workout_status`
   (`tools/today_status.py`) is read-only. When no plan document exists
   for today, it reports `"no_plan"` and stops — there is no tool the
   LLM is allowed to call to fix this in the same conversation. The only
   path forward is a manual Streamlit button ("Set Week Themes"), which
   itself only sets the *month's* theme path, not the missing week's
   actual block structure — the user has to ask again afterward.
2. **`update_three_day_plan` categorically refuses `date == today`.**
   This rule exists deliberately, to protect eval integrity: once a plan
   is set for a day, the coach shouldn't be able to silently rewrite it
   out from under the user mid-stream. That protection is correct for
   any day that already has a plan. But it also blocks the one case
   where there's nothing to protect — a day that never had a plan
   written for it in the first place, because nobody was using the app
   in the days prior to prepare it in advance.
Both symptoms have the same root cause: the chain has no self-repair
step. It only knows how to extend forward from an existing state, never
how to notice and fill a state that was never established.
 
## What "Backfill" Means Here
 
When a user asks the coach about today's workout and no plan exists,
the coach should — in that same turn — reconstruct what *would* have
existed if the user had never missed time, and pick up the normal
rolling-plan rhythm from there:
 
- **This week's structure**, if missing, gets generated from the
  month's already-set theme path (or, if the month itself has no theme
  path yet, that gets generated first — same as it would through the
  normal flow, just without the manual button click).
- **Today's plan specifically** gets generated once, through a narrow
  carve-out — not a general loosening of the "never rewrite today" rule.
  The carve-out applies only when no plan document exists for today at
  all. Any day that already has a document (planned, completed, or
  rest) is completely untouched by this feature; the existing
  protection against silently rewriting an established day's plan stays
  exactly as strict as it is today.
- **The normal forward window** (tomorrow, day+2, day+3) gets generated
  in the same turn, so the user isn't just unblocked for today — they're
  fully caught back up to the normal cadence, and every subsequent turn
  behaves exactly as if no gap had ever happened.
The result the user should feel: they ask for today's workout after any
length of absence, and get one, in one turn — with no error message, no
manual button, and no second ask.
 
## In Scope
 
- Detecting, at the point today's workout is requested, that no plan
  document exists for today.
- Reconstructing whatever upstream state is missing to make that
  possible: month theme path (if absent) → this week's block structure
  (if absent) → today's plan → the forward tomorrow/day+2/day+3 window.
- A narrow, explicit carve-out for same-day plan generation that fires
  only in the true "never existed" case — not a relaxation of the
  existing protection for days that already have a document.
- Reusing existing generation/validation logic (week theme generation,
  block-target calculation, the exercise-plan schema and its warmup/
  main/cooldown/duration checks) rather than a parallel, looser code
  path — a backfilled plan should be structurally indistinguishable
  from one generated through the normal flow.
- Leaning on V9.2's retry/re-prompt/guarded-write machinery for every
  LLM call and Mongo write this introduces, rather than bespoke error
  handling for this feature specifically.
## Out of Scope
 
- Any retroactive plan generation for days that have already passed.
  A gap of missed days in the past is not filled with workout plans —
  there's nothing meaningful to backfill there.
- Any coach-voice acknowledgment of a past gap ("looks like it's been a
  while...") — a UX/tone decision, not a planning-logic one. Can be
  considered separately, doesn't block this version.
- Any change to `sync_backlog` or backlog handling — a missed *planned*
  day still flows through the existing backlog sweep exactly as today;
  this version only concerns days that never had a plan document at all.
- Any change to the "never rewrite an existing day" protection itself.
- A scheduled/unattended trigger for any of this (that's V9.4's remit).
## Open Items for Design Phase
 
- Whether a backfilled plan/week doc needs any marker distinguishing it
  from a normally-generated one (for later debugging/auditing), or
  should be fully indistinguishable.
- Exact failure behavior if reconstruction succeeds through, say, week
  structure but then fails on today's plan generation or the forward
  window — how much of a partial success gets persisted vs. discarded,
  and what the user sees.
- Where in the graph/tool-call flow reconstruction is triggered from —
  a decision explicitly deferred to design, now that scope no longer
  assumes a specific implementation shape.
