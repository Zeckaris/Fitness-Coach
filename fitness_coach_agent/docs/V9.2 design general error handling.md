# V9.2 — General Error Handling: Design Document
 
**Status:** Design (pre-implementation)
**Git tag target:** `v1.2.0` (prerelease)
**Depends on:** none (builds on V9.0's `auth/context.py` pattern for shared, call-site-agnostic helpers)
**Blocks:** V9.3 (backfill logic), V9.4 (proactive scheduling), and all subsequent V9.x versions
 
---
 
## Problem Statement
 
Failure handling today is inconsistent and, in places, absent:
 
- `agent/graph.py` has no failure handling at all. A node throwing mid-run
  propagates as a raw exception with undefined behavior at the `.invoke()`
  call site.
- `agent/monthly_review.py`'s two `.with_structured_output()` call sites
  (`_generate_review`, `generate_theme_path`) each use a blanket
  `except Exception`, conflating three distinct failure types (Gemini
  network/timeout failure, structured-output validation failure, and
  anything else) that this scope treats differently. `_generate_review`
  has no fallback at all — it re-raises on any failure. `generate_theme_path`
  has a fallback (a hardcoded theme chain) but reaches it immediately on
  first failure, with no retry attempted first.
- Mongo- and AstraDB-touching tool functions in `tools/` have no explicit
  handling for connection-level failures; a dependency outage and an
  ordinary "no document found" case are not currently distinguished.
- No coach-voice fallback messaging convention exists anywhere in the
  codebase.
This must be resolved before V9.3 (backfill logic) and V9.4 (unattended,
scheduled execution via Telegram) introduce more surface area for
failures to go unhandled.
 
## Non-Goals
 
- No change to the existing tool-argument validation pattern
  (`@tool(args_schema=...)` in `tools/month_plans.py` and elsewhere).
  LangChain's built-in behavior — a validation error becomes a
  `ToolMessage` the LLM sees and can self-correct against on its next
  turn — already works and needs no new wrapper.
- No exponential backoff or configurable retry counts. Retry policy is
  fixed and uniform: **one retry**, full stop.
- No structured logging/observability platform change. Existing Langfuse
  tracing (`CallbackHandler`) is unchanged.
- No user-facing error telemetry UI (toasts, dashboards). Errors surface
  as coach-voice chat messages, or — for the monthly review pipeline
  specifically — as a plain status message in the Streamlit admin action
  that triggered it.
## Architecture
 
### 1. Failure taxonomy
 
Three distinct failure types, replacing blanket `except Exception`
wherever they're currently conflated:
 
| Type | Definition | Handling rule (per scope) |
|---|---|---|
| **A — Gemini call failure** | SDK-level error or timeout, before any output parsing | Single retry, then fallback |
| **B — Structured-output validation failure** | LLM responded; `.with_structured_output()` parsing/Pydantic validation failed | Re-prompt once with the validation error, then fallback |
| **C — Dependency failure** | Mongo or AstraDB connection/query failure | Mongo: hard-fail cleanly, no silent partial writes. AstraDB: isolated to `search_fitness_knowledge_base`, rest of the agent unaffected |
 
### 2. New shared module: `agent/error_handling.py`
 
Two call-site-agnostic helpers, used everywhere Type A / Type B failures
can occur:
 
```python
def call_llm_with_retry(llm, messages, **invoke_kwargs):
    """Type A handling. One retry on failure/timeout.
    Raises LLMCallFailed if both attempts fail — caller decides the fallback."""
 
def call_structured_llm_with_reprompt(llm, prompt, output_schema, **invoke_kwargs):
    """Type B handling. On validation failure, re-invokes once with the
    validation error appended to the prompt. Raises StructuredOutputFailed
    if the second attempt also fails validation — caller decides the fallback."""
```
 
Two new typed exceptions (`LLMCallFailed`, `StructuredOutputFailed`) let
callers distinguish "give up and use my fallback" from any other bug,
rather than catching bare `Exception`.
 
Fallback behavior is deliberately **not** baked into these helpers — it
stays at each call site, since the right fallback differs by context
(see below).
 
### 3. `coach_node` (agent/graph.py)
 
Wrap the existing `llm.invoke(messages)` with `call_llm_with_retry`.
On `LLMCallFailed`, `coach_node` catches it internally and returns a
fallback `AIMessage` in coach voice (e.g. "I'm having trouble thinking
this through right now — give me a moment and try again.") instead of
raising. Because `coach_node`'s contract is "always return `messages`,"
this keeps the graph's control flow simple: a plain-text fallback
response routes through `tools_condition` straight to `END`, exactly
like any other non-tool-calling reply. No plan-altering side effects
occur, and the user sees one coach-voice message — this satisfies "halt
the turn" without needing new conditional edges.
 
### 4. `backlog_sync_node` and `goal_context_node` (critical, halt)
 
Neither node needs internal try/except. LangGraph does not swallow node
exceptions by default — an unhandled exception in either node already
propagates naturally up through `.invoke()`. The new work is entirely at
the **invoke call site** (`app/components/chat.py`, where
`compiled_workflow.invoke(...)` is called): wrap that call in try/except,
and on exception, render a coach-voice fallback message directly in the
UI without ever reaching `coach_node`. This is the "halt" behavior in
practice — no graph restructuring required.
 
### 5. `history_check_node` (non-critical, continue)
 
The one node needing an internal try/except that *swallows* rather than
propagates. On failure, return `{"history_checked": True,
"yesterday_context": None}` — same shape as the success path, so
`backlog_sync_node` and everything downstream proceed exactly as if no
checkin history existed for yesterday.
 
### 6. Tool-level handling (not node-level)
 
`tools` is a single `ToolNode` wrapping 18 functions with different
dependency profiles — criticality doesn't attach to the node, it attaches
to each tool's dependency. Two shared decorators cover this instead of
per-tool duplication:
 
- **`@mongo_guarded`** — applied to tool functions that touch Mongo
  (`update_three_day_plan`, `stage_month_goal`, `confirm_month_goal`,
  `update_week_plan`, and the read-only tools). Catches
  connection/timeout-level pymongo exceptions specifically (not
  generic `Exception` — an ordinary "no document found" is not a
  failure) and returns a uniform string: *"I couldn't reach your saved
  data just now — please try again in a moment."* This avoids two
  problems at once: a raw pymongo traceback reaching the LLM as tool
  output, and the ReAct loop blindly re-calling a tool against a
  dependency that's actually down.
- **`@astradb_guarded`** — applied to `search_fitness_knowledge_base`
  only. On failure, returns an empty/degraded result (no error string)
  so the agent proceeds without retrieved context, consistent with
  AstraDB being isolated and non-critical per scope.
### 7. `agent/monthly_review.py`
 
- **`_generate_review`**: wrap the `.with_structured_output(MonthlyReviewOutput)`
  call with `call_structured_llm_with_reprompt`. Currently this function
  has *no* fallback — it re-raises. New fallback, reached only once
  retry + re-prompt are both exhausted:
  `{"narrative": "This month's review couldn't be generated automatically.",
  "coaching_context": ""}`.
- **`generate_theme_path`**: same wrapper. The existing hardcoded fallback
  chain (`Volume → Intensity → Volume → Peak → Deload`) is preserved
  as-is and untouched — it now triggers only after retry + re-prompt are
  exhausted, instead of on the first exception.
- **`close_out_month`** / **`refresh_week_themes`**: their direct Mongo
  calls get the same `@mongo_guarded` treatment as the tools above, for
  consistency — Mongo failure here should also hard-fail cleanly rather
  than partially update a month-plan document.
- **`run_monthly_review()`**: confirmed as a manual Streamlit admin
  action, not yet a scheduled job. The whole call gets wrapped in
  try/except at the Streamlit component level. On any propagated
  `LLMCallFailed` / `StructuredOutputFailed` / Mongo failure, the UI
  displays a plain status message (not a stack trace) rather than
  crashing the Streamlit session. This boundary will need revisiting
  once V9.4 moves this pipeline to an unattended cron trigger, since
  there's no chat UI to render into at that point.
 
## Open Items for Implementation Phase
 
- Exact wording of coach-voice fallback messages — not yet decided,
  low-stakes, can default to simple variants unless otherwise specified.
- Whether `@mongo_guarded` / `@astradb_guarded` are implemented as
  decorators or as a shared context-manager — implementation-phase
  choice, no design risk either way.
- Whether `LLMCallFailed` / `StructuredOutputFailed` need Langfuse-visible
  tagging (so failures are traceable in existing traces) — likely yes,
  needs confirming during implementation.


  














## Addendum (added during implementation, pre-v1.2.0 tag)

Two changes made mid-implementation that go beyond the original design:

### 1. `agent/llm.py` — extracted LLM client construction

Raw `ChatGoogleGenerativeAI(...)` construction (model name + temperature)
moved out of `agent/graph.py` and `agent/monthly_review.py` into a new
shared module, `agent/llm.py`:

- `build_coach_llm(api_key)` — `gemini-3.5-flash-lite`, temperature 0.4.
  Tool-binding (`.bind_tools(TOOLS)`) stays in `graph.py`, since `TOOLS`
  is graph-specific.
- `build_review_llm(api_key)` — `gemini-3.5-flash`, temperature 0.3.

Both take `api_key` as a parameter rather than reading `GEMINI_API_KEY`
internally, so they can serve as the `llm_factory` callables that
`call_llm_with_retry` / `call_structured_llm_with_reprompt` use to
rebuild a client against a different key (see below).

### 2. API key rotation on rate-limit / model-unavailable failures

**Motivation:** in practice, Gemini rate limits (429) were hit often
enough during development that they were being handled manually — by
swapping the API key by hand. This is now automated, and extended to
cover an adjacent failure the manual process didn't: some configured
keys are on tiers where certain model names return "model not found"
(404) rather than a rate-limit error, since Google has been retiring
availability of some models per-tier. Both cases mean *this key cannot
serve this request at all*, so both trigger rotation rather than a
same-key retry.

**Config:** keys are read from `GEMINI_API_KEY_1`, `GEMINI_API_KEY_2`,
... (sequential, stops at the first missing number), falling back to a
single `GEMINI_API_KEY` if no numbered keys are set. Managed in
`agent/error_handling.py`'s module-level `ApiKeyPool` — shared across
all sessions/users, since rate limits and model availability are
properties of the key, not the user.

**Behavior:**
- Rate-limit (429) or model-not-found (404) failure → rotate to the
  next key in the pool, retry the same request. This continues for at
  most **one full cycle** through the remaining configured keys, then
  gives up and raises (`LLMCallFailed` / `StructuredOutputFailed`) —
  it does not keep cycling indefinitely, since a rate limit typically
  doesn't clear for ~24h and a second pass through the same keys would
  be pointless.
- Any other failure (timeout, transient network error, etc.) → a
  single same-key retry, unchanged from the original design.
- For `call_structured_llm_with_reprompt` specifically: a validation
  failure (the key worked, the output didn't parse) still gets a
  same-key re-prompt with the validation error appended, exactly as
  originally designed. Key rotation only fires for the "this key can't
  serve this request" case, not for validation failures.
